Guia visual da arquitetura do backend

Regra Central

A arquitetura segue uma ideia de ports and adapters. O centro da aplicação não conhece os detalhes externos. O Domain não sabe que existe HTTP, banco, JWT ou Swagger. A Application sabe o que precisa fazer, mas fala com interfaces. A Infrastructure equipa essas interfaces com tecnologias reais.

Api -> Application -> Domain Infrastructure -> Application + Domain

Regra de ouro

Se uma decisão é regra de negócio ou fluxo de aplicação, ela fica em Domain ou Application. Se uma decisão é detalhe de ferramenta, como PostgreSQL, JWT ou EF Core, ela fica em Infrastructure.

Diagramas da Arquitetura

A leitura geral fica assim: a requisição entra pela API, passa pela Application, consulta o Domain quando precisa de regras e usa a Infrastructure para acessar banco, storage, autenticação e outros serviços externos.

A

Entrada HTTP

ServiceLifeOS.Api recebe comandos do mundo externo: rotas, headers, token, tenant e Swagger.

S

Casos de Uso

Application coordena fluxos como login, CRUD, transação e DTOs.

R

Regras Puras

Domain guarda entidades e regras puras. Ele não sabe que banco ou HTTP existem.

E

Adapters Externos

Infrastructure usa PostgreSQL, EF Core, JWT e hash de senha para cumprir os ports.

Caminho de uma requisição

Cada bloco passa só a informação necessária para o próximo. O objetivo é não deixar uma camada fazer o trabalho da outra.

Cliente Faz HTTP com token e tenant.
Controller Converte requisição em chamada de service.
Service Orquestra o caso de uso e usa ports.
Domain Entidades e regras puras.
Adapter EF Core, JWT ou hash.
DTO Resposta volta limpa para a API.

As Quatro Camadas Principais

Uma requisição entra pela API, passa pelo caso de uso na Application, usa regras do Domain quando necessário e acessa recursos externos pela Infrastructure.

Camada 1

ServiceLifeOS.Api

Entrada HTTP. Recebe requisições, autentica, resolve tenant, chama casos de uso e devolve respostas.

Camada 2

ServiceLifeOS.Application

Casos de uso. Orquestra fluxos, usa ports, DTOs e services, mas não conhece EF Core nem ASP.NET.

Camada 3

ServiceLifeOS.Domain

Modelo de domínio. Entidades e regras puras vivem aqui, sem dependência de banco, web ou storage.

Camada 4

ServiceLifeOS.Infrastructure

Implementações externas. Implementa banco, JWT, hash de senha, migrations e repositórios EF.

O Que Cada Pasta Resolve

Use esta referência para decidir onde colocar código novo. Pense sempre: isto é entrada, caso de uso, regra ou integração externa?

src/ServiceLifeOS.Api

Função: adaptar HTTP para os casos de uso internos.

  • Controllers: recebem requisições como /auth/login e /examples.
  • Middleware: resolve e valida tenant antes da requisição entrar no caso de uso.
  • Adapters: transforma contexto HTTP em interfaces como ICurrentUser e ICurrentTenant.
  • OpenApi: ajusta Swagger, headers e documentação da API.
  • Program.cs: inicializa a aplicação, registra DI, auth, CORS, migrations e controllers.

src/ServiceLifeOS.Application

Função: executar missões de negócio sem depender de tecnologia externa.

  • Services: casos de uso. Exemplo: criar item e login.
  • Ports: contratos que a Application precisa. Exemplo: repositório, token e hash.
  • Dtos: formato de entrada e saída dos casos de uso.
  • Options: configurações que pertencem ao comportamento da aplicação.
  • DependencyInjection.cs: registra services da Application.

src/ServiceLifeOS.Domain

Função: guardar as coisas que seriam verdade mesmo sem web ou banco.

  • Entities: modelos centrais como ExampleItem, AppUser e UserTenantAccess.
  • Services: regras puras, como limites de nome e descrição.
  • Não coloque EF Core, Controller, JWT ou configuração de HTTP aqui.
  • Se você pudesse testar com um new simples, provavelmente pode morar no Domain.

src/ServiceLifeOS.Infrastructure

Função: conversar com o mundo real usando ferramentas concretas.

  • Persistence: AppDbContext, configurações EF, seed e repositórios.
  • Identity: JWT e hash PBKDF2.
  • Options: configurações de JWT.
  • Migrations: histórico de evolução do schema do PostgreSQL.
tests
A área de treino. Testa regras de Domain e garante que as camadas não ganharam dependências proibidas.
docs
Documentação técnica. Explica decisões, diagramas e convenções para você voltar depois e lembrar por que algo existe.
docker-compose
Ambiente local. Sobe o PostgreSQL para desenvolvimento.

Como as Pastas se Combinam

Aqui estão os caminhos mais importantes. Eles mostram como uma ação passa pelas camadas sem quebrar a regra das dependências.

Fluxo: criar um item

1. API

ExamplesController recebe o JSON e chama ExampleItemService.

2. Application

O service valida o caso de uso, usa ICurrentTenant e prepara a entidade.

3. Domain

ExampleItem representa a entidade e regras puras limitam campos.

4. Infrastructure

ExampleItemRepository salva no PostgreSQL via EF Core.

5. Retorno

O service devolve DTO para a API responder HTTP.

Onde Eu Devo Fazer Cada Coisa?

Use esta tabela como referência. Antes de criar arquivo novo, procure qual tipo de alteração combina com sua necessidade.

Nova rota HTTP
Crie ou altere um controller em ServiceLifeOS.Api/Api/Controllers. O controller deve ser fino: receber, chamar Application e devolver resposta.
Novo caso de uso
Crie um service em ServiceLifeOS.Application/Application/Services. Exemplo: InvoiceService e AuthService.
Nova regra pura
Coloque no ServiceLifeOS.Domain. Se a regra não precisa de banco, requisição HTTP ou SDK externo, ela pertence ao domínio.
Novo acesso a banco
Primeiro crie uma interface em Application/Ports. Depois implemente em Infrastructure/Persistence/Repositories.
Nova tabela
Crie a entidade no Domain, configure EF em Infrastructure/Persistence/Configurations, adicione DbSet no AppDbContext e gere migration.
Novo adapter externo
Email, fila, cache, JWT, hash ou API externa entram em Infrastructure. A Application só deve enxergar uma interface.
Exemplo de funcionalidade: "quero adicionar notificações por email" 1. Application/Ports: criar IEmailSender 2. Application/Services: chamar IEmailSender no caso de uso certo 3. Infrastructure: implementar SmtpEmailSender ou SendGridEmailSender 4. Infrastructure/DependencyInjection.cs: registrar IEmailSender 5. Api: se precisar, criar endpoint que dispara o caso de uso 6. Tests: testar regra e dependência de camadas

Como Criar Uma Funcionalidade Nova

Comece identificando se a integração externa já existe na Infrastructure. Se existir, reutilize o port disponível. Se não existir, crie o port na Application e implemente o adapter correspondente na Infrastructure.

1

Exemplo B: endpoint novo quando o adapter ainda não existe

Objetivo: criar POST /videos que dispara um transcodificador externo para gerar versões menores.

Payload de entrada

POST /videos { "title": "aula-01" }

Não existe um port como IVideoTranscoder. Esse contrato precisa ser criado.

Caminho da implementação

  1. Domain: crie a entidade que representa o vídeo, por exemplo VideoAsset, com TenantId.
  2. Application/Ports: crie IVideoTranscoder com o contrato necessário, sem citar SDK externo.
  3. Application/Services: crie VideoService; ele agenda ou transmite a transcodificação.
  4. Dtos: crie payload e response em Application/Dtos/Videos.
  5. Infrastructure: implemente IVideoTranscoder, por exemplo CloudVideoTranscoder ou FfmpegVideoTranscoder.
  6. DependencyInjection: registre IVideoTranscoder apontando para o adapter real.
  7. Persistence: crie repository/configuration/migration se o vídeo tiver tabela própria.
  8. Api: crie VideosController chamando só o VideoService.

Regra mental

Quando a ferramenta ainda não existe, não coloque o SDK externo dentro da Application. Primeiro defina o contrato que você quer usar: o port. Depois construa a implementação real na Infrastructure.

Cuidados de Arquitetura

Não coloque regra pesada no Controller

Controller é uma camada de entrada. Ele não deve decidir a estratégia inteira do caso de uso. Se tiver if de regra de negocio, provavelmente pertence a Application ou Domain.

Não deixe o Domain conhecer ferramentas

Se aparecer DbContext, HttpContext ou Jwt no Domain, a regra de dependência entre camadas foi quebrada.

Use ports para respeitar limites entre camadas

Application fala com interfaces. Infrastructure implementa. Assim você consegue trocar ferramenta sem reescrever a aplicação inteira.

Tenant é chave de segurança

Dados tenant-aware precisam ter TenantId, filtro global quando aplicável, e paths de storage com tenants/{tenantId}/.

Checklist antes de commitar uma feature

[ ] A API só adapta HTTP? [ ] A Application orquestra sem depender de ASP.NET ou EF Core? [ ] O Domain continua puro? [ ] A Infrastructure implementa os ports? [ ] Entidade tenant-aware tem TenantId e filtro/consulta segura? [ ] Migration foi gerada e aplicada? [ ] Build e testes passam?
